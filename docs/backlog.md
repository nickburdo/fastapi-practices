# Бэклог: кандидаты на будущие задачи

Сюда записываются найденные проблемы и идеи, которые не вошли ни в один план. Пункт из бэклога — ещё не решение:
перед работой по нему пишется отдельный план в `docs/plans/` и согласовывается как обычно.

## Пользователи и аутентификация

Источник: код-ревью ветки `feature/auth-jwt` (план `docs/plans/users-auth-plan.md`), 2026-11-02. Для учебного
проекта на SQLite ни один пункт не критичен; все становятся важными при реальной нагрузке или выкладке.

| # | Проблема | Где | Чем грозит | Возможное решение |
|---|---|---|---|---|
| B1 | Гонка при регистрации: два одновременных запроса с одним `username` оба проходят проверку «имя свободно» | `users/services.py` → `register_user` | Второй запрос падает на уникальном индексе: `500` вместо `409 "Username already taken"`. Уже записано в «Вне рамок» плана | Ловить `sqlalchemy.exc.IntegrityError` при `flush`/`commit` и превращать в `UsernameTakenError` |
| B2 | Argon2 синхронный и тяжёлый (64 МБ памяти, 3 прохода), а вызывается прямо внутри `async def` | `users/security.py`, вызовы из `users/services.py` | Каждый вход/регистрация блокирует event loop на ~50–100 мс; пачка запросов на вход (в том числе с несуществующими именами — проверка `DUMMY_HASH`) тормозит все остальные роуты | Выполнять хэширование и проверку в пуле потоков: `fastapi.concurrency.run_in_threadpool` или `anyio.to_thread.run_sync` |
| B3 | У пароля нет `max_length` | `users/schemas.py` → `UserCredentialsSchema.password` | Без входа можно отправить пароль в несколько МБ; вместе с B2 — дешёвый способ нагрузить CPU и весь API | `Field(min_length=1, max_length=128)` (или другой разумный предел) |
| B4 | Миграция всегда создаёт админа `admin` / `admin`, пароль известен из README | `migrations/versions/27139778c693_create_users_table.py` | В любой среде после `alembic upgrade head` есть админ с публичным паролем, который может удалять пользователей. Для учебного проекта выбрано сознательно (решение A3 плана) | Создавать админа отдельной CLI-командой с паролем из `.env`/ввода, а не в миграции; или требовать смену пароля при первом входе |
| B5 | Имена пользователей не нормализуются: нет обрезки пробелов и приведения регистра; уникальность в SQLite регистрозависима | `users/schemas.py` → `UserCredentialsSchema.username` | Можно зарегистрировать `Admin`, `admin ` и т. п. рядом с `admin` — похожие имена путают при выборе `user_id` для удаления | Продуктовое решение: `str_strip_whitespace=True` и/или хранить имя в нижнем регистре (или регистронезависимый уникальный индекс) |

Другие отложенные вещи из того же плана (logout, смена пароля, `GET /users/{user_id}`, refresh-токены, CORS,
назначение админа через API, тесты) перечислены в его разделе «Вне рамок».

## Файлы

Источник: план `docs/plans/files-module-plan.md` (решение F17 — B6) и код-ревью ветки `feat/files-module`
(B7–B11), 2026-11-03. Для учебного проекта ни один пункт не критичен.

| # | Проблема | Где | Чем грозит | Возможное решение |
|---|---|---|---|---|
| B6 | При удалении пользователя его файлы остаются: внешние ключи в SQLite не включены, `files.owner_id` указывает на удалённого пользователя | `users/services.py` → удаление пользователя; `files/models.py` | Записи и файлы на диске копятся; видит и может удалить их только админ. Новому пользователю они не достанутся: id не переиспользуются (`sqlite_autoincrement`) | Удалять файлы пользователя (записи и диск) в сервисе удаления пользователя; или включить `PRAGMA foreign_keys=ON` + `ondelete="CASCADE"` и отдельно чистить диск |
| B7 | Ошибка удаления файла с диска превращается в `500`, хотя запись в БД уже удалена; при очистке после неудачной загрузки одна такая ошибка прерывает удаление остальных файлов | `files/services.py` → `delete_file`, `upload_files` (цикл в `except`) | В Windows `unlink` падает с `PermissionError`, если файл в этот момент скачивают. Клиент видит `500` при фактически успешном удалении, повтор даёт `404`, файл остаётся на диске навсегда | Обернуть `storage.delete` в `try/except OSError` (с записью в лог) и всё равно отвечать `204`; в цикле очистки продолжать после ошибки |
| B8 | Гонка при скачивании: файл удалён между `storage.exists` и отправкой `FileResponse` | `files/services.py` → `get_file`; `files/routes.py` → `download_file` | Starlette бросает `RuntimeError("File at path ... does not exist.")` → `500` вместо `404`. Нужен параллельный `DELETE`, поэтому маловероятно | Открывать файл заранее и отдавать поток (`StreamingResponse`) или ловить ошибку на уровне приложения |
| B9 | `created_at` без часового пояса: SQLite пишет UTC (`CURRENT_TIMESTAMP`), а API отдаёт `2026-11-03T12:16:06` без смещения | `files/models.py`, `files/schemas.py` | Клиент прочитает время как местное и покажет его со сдвигом | Отдавать с `Z`/`+00:00` (сериализатор в `FileSchema`) или хотя бы описать в README |
| B10 | Отмена запроса во время загрузки (остановка сервера, `asyncio.CancelledError`) не очищает уже записанные файлы: `except Exception` не ловит `BaseException` | `files/services.py` → `upload_files` | На диске остаются файлы без записей в БД | `except BaseException` с очисткой (учитывая, что `await` внутри обработчика отмены сам может быть отменён) |
| B11 | Проверка типа по Content-Type (решение F5) отклоняет и законные загрузки: браузер на Windows берёт MIME-тип из реестра, и без Office шлёт для `.docx`/`.xlsx` `application/octet-stream`; некоторые клиенты шлют `image/jpg`/`image/pjpeg` для JPEG | `files/validation.py` → `ALLOWED_TYPES`, `check_upload` | Пользователь получает `415` для обычного документа или фото | Допускать для расширения несколько MIME-типов (в том числе `application/octet-stream` для офисных), или проверять содержимое по первым байтам (библиотека `filetype`) |
