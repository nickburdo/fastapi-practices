## Этап 1. Файл исключений `.gitignore`

> **Зачем.** Git должен хранить только код и документы. Окружение (`.venv` — сотни мегабайт),
> кэши, база данных, личные настройки IDE и `.env` (в нём могут быть пароли) — не нужны или опасны.

**1.1.** Создать в корне проекта файл `.gitignore`:

```gitignore
# Python
__pycache__/
*.py[cod]

# Virtual environment
.venv/

# Tools
.ruff_cache/

# Local settings and data
.env
books.db

# IDE
.idea/
```

## Этап 2. Создание репозитория

**2.1.** В терминале в корне проекта — создать репозиторий с веткой `main` (G3):

```
git init -b main
```

**2.2.** Почта автора — noreply, **только для этого репозитория** (G5). Имя берётся из глобальных настроек:

```
git config user.email "72523519+nickburdo@users.noreply.github.com"
```

**2.3.** Проверить:

```
git config user.name
git config user.email
```

Ожидаемо:

```
Mykola Burdo
72523519+nickburdo@users.noreply.github.com
```

## Этап 3. Первый коммит

**3.1.** Посмотреть, что git собирается взять:

```
git status
```

Ожидаемо в списке `Untracked files` — **только**:

```
.env.example
.gitignore
books/
docs/
main.py
pyproject.toml
shared/
```

**Если в списке есть `.venv/`, `.idea/`, `books.db`, `.ruff_cache/` или `__pycache__/`** — `.gitignore`
не сработал (не то имя файла или не та папка). Остановиться, не коммитить.

**3.2.** Добавить файлы и закоммитить (G8):

```
git add .
git commit -m "Initial commit"
```

При `git add` возможны предупреждения `LF will be replaced by CRLF` / `CRLF will be replaced by LF` —
это нормально для Windows, не ошибка.

**3.3.** Проверить автора коммита:

```
git log --format="%h %an <%ae> %s"
```

Ожидаемо — одна строка с `<72523519+nickburdo@users.noreply.github.com>` и `Initial commit`.

## Этап 4. Публикация на GitHub — ОТЛОЖЕН (G10)

> Не выполнять, пока пользователь не решит публиковать. Если к тому времени появятся
> ветки задач — сначала влить их в `main` локально, затем выполнить этап.
> Перед публикацией повторить проверку на секреты (пароли, токены, рабочая почта).

**4.1.** Создать публичный репозиторий и отправить в него коммит одной командой (G1, G6, G7):

```
gh repo create fastapi-as --public --source=. --remote=origin --push --description "Learning project: books API on FastAPI + async SQLAlchemy"
```

- `--source=.` — взять текущий локальный репозиторий;
- `--remote=origin` — назвать связь с GitHub `origin` (стандартное имя);
- `--push` — сразу отправить коммиты.

**4.2.** Проверить связь:

```
git status
```

Ожидаемо: `Your branch is up to date with 'origin/main'.`

**4.3.** Открыть репозиторий в браузере и убедиться, что файлы на месте, а `.venv`, `.idea`, `books.db` — нет:

```
gh repo view --web
```

## Этап 5. Дальнейшая работа (для справки)

> Каждая задача — в своей ветке; в `main` напрямую не коммитим (G9).

**Пока репозиторий только локальный:**

| Задача | Команда |
|---|---|
| Начать задачу | `git switch main` → `git switch -c <ветка>` |
| Посмотреть изменения | `git status`, `git diff` |
| Сохранить шаг работы | `git add .` → `git commit -m "..."` |
| Влить задачу в `main` | `git switch main` → `git merge --no-ff <ветка>` |
| Удалить влитую ветку | `git branch -d <ветка>` |

`--no-ff` сохраняет в истории отдельный «коммит слияния» — видно, какие коммиты относились к задаче.

**После публикации на GitHub (этап 4):**

| Задача | Команда |
|---|---|
| Начать задачу (от свежего `main`) | `git switch main` → `git pull` → `git switch -c <ветка>` |
| Отправить ветку на GitHub | `git push -u origin <ветка>` |
| Открыть Pull Request | `gh pr create --fill` |
| Влить в `main` и удалить ветку | `gh pr merge --merge --delete-branch` |
| Вернуться на обновлённый `main` | `git switch main` → `git pull` |
